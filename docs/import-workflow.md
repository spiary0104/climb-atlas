# Gym import workflow

How new gyms get from research into production. **Stage 5 status: validation, dry-run and review are built and tested;
the production import step is deliberately NOT built yet** (see "Production import (not built)").

```
research → import/batches/<batch>/records.ndjson   (staging; one gym per line)
        → validate   (offline schema checks)
        → plan       (dedupe vs the match index → plan.json + report.md; dry-run, never writes to production)
        → freeze-ids (write the g-<hex> ids into the batch once)
        → review     (a human reads report.md; decisions.json resolves probable duplicates)
        → import     (NOT BUILT: explicit, gated, separate command; needs approval)
```

## Directory layout
```
import/
  index/gym-index.ndjson     Lightweight match index of PRODUCTION gyms (id,name,country,state,suburb,lat,lng,address,types,h). ~480 KB. Derived, never hand-edited.
  index/index-meta.json      count + sha256 of the index, and where it was built from
  batches/<YYYY-MM-DD-slug>/
    batch.json               {schema_version:1, batch_id, description, created}
    records.ndjson           the research output: one JSON object per line (append-only while researching)
    decisions.json           (optional) human decisions on probable duplicates
    plan.json / report.md    generated by `plan` (deterministic: no timestamps, byte-identical on rerun)
    manifest.json            written by the future import step; its presence marks the batch as imported
scripts/gym-import.js        CLI (new-batch, validate, plan, freeze-ids, build-index, verify-index)
scripts/lib/gym-import/      normalize, validate, match, plan, report, index-store
tests/import-*.test.js       regression tests (run: node --test "tests/*.test.js")
```
`data/gyms.json` is **legacy**: not read, written or needed by the pipeline. `data/gyms.reconciled.json` is an untracked
Stage 0 artefact used only as a test fixture (tests skip themselves if it is absent).

## Adding a research batch
```
node scripts/gym-import.js new-batch japan-osaka-round-1 --description "Osaka gyms from chain store lists"
# append records (never open/read old data): one JSON object per line
echo '{"name":"...","suburb":"...","state":"OSAKA","country":"JP","lat":34.69,"lng":135.50,"types":["indoor-bouldering"],"address":"...","notes":"...","photo":null}' >> import/batches/<batch>/records.ndjson
node scripts/gym-import.js validate <batch>       # offline; exit 1 on any error
node scripts/gym-import.js plan <batch>           # writes plan.json + report.md; exit 0 = importable, 2 = needs work
node scripts/gym-import.js freeze-ids <batch>     # once the report is clean; then plan again
```
`<batch>` is a directory or just its name under `import/batches/`. Read `report.md` (small, capped), not `records.ndjson`.

**Record (new gym):** `name, suburb, state, country, lat, lng, types` required; `address, notes, photo` optional; `id` only
after `freeze-ids`; `source` (free text, not stored) recommended. `country` = 2-letter code; `state` must be a code from
`js/modules/regions.js`; `types` ⊆ `indoor-bouldering | top-rope | lead-climbing`; `lat/lng` JSON numbers; `photo` a plain
http(s) URL (same `safeUrl` rule as the app). Any other field (`status`, `community: true`, `edited`, typos…) is an error.
**Record (update existing gym):** `{"intent":"update","id":"<existing id>","reason":"why","set":{"types":[...]}}` — only
`name, suburb, state, lat, lng, types, address, notes, photo` may be set; a full record that differs from an existing gym is
never treated as an update.

## Classes (what the plan says will happen)
| Class | Meaning | Production effect |
|---|---|---|
| `new` | Not in production, not a candidate duplicate | would insert |
| `existing` | Same gym already in production (identical or content-differs) | none — never overwritten |
| `update` | Explicit `intent:"update"` record for an existing id | would update the listed fields only |
| `probable-duplicate` | Might be an existing/staged/in-batch gym; a human must decide | blocks the plan |
| `invalid` | Fails validation (message says which field and why) | blocks the plan |
| `rejected` | A human decided `reject` | none |

A plan is **importable** only when there are no invalid records, no unresolved probable duplicates, every new record has a
frozen id, every decision applies to something, and there is at least one insert/update.

## Duplicate detection (`scripts/lib/gym-import/match.js`, one threshold table)
Compares each record with the index gyms of the **same country** (and with other not-yet-imported batches and other records in the
same batch). Never uses array position or the numbering of `seed-*` ids; an id is only a hint that must be confirmed by content.
- **existing** — same normalised name within 1 km (pin differences are reported, production pin kept); or same address + related
  name within 10 km; or an id that resolves to a production gym whose name is equal / pin within 150 m.
- **probable** (human review) — same name 1–15 km away, or same suburb+state at any distance; related name (rebrand/translation)
  within 100 m; same address but different name within 500 m; anything within 60 m; partly similar name within 250 m;
  a second `existing` candidate that is not clearly further away (ambiguous chain branches).
- Names are compared case/accent/punctuation-insensitively with `( … )` translations ignored and generic words (climbing, gym…)
  dropped for similarity. Addresses in a different language/script do not match — the name/distance rules cover that.
- Both sides of an in-batch pair are flagged, so the result never depends on line order.
Also warns (never blocks): coarse coordinates, a gym >1,500 km from any known gym in its country, unsupported countries,
content that differs from an existing gym.

## IDs
New gyms get `g-<first 10 hex of sha1(country|name|suburb|lat(4dp)|lng(4dp))>` using the reconciliation's own normalisation
(so the 249 ids frozen in Stage 0 re-derive exactly — tested). Collisions extend by 2 hex chars, resolved in sorted order so
the result is independent of record order. `freeze-ids` writes the id into `records.ndjson` **once**; after that, edits to the
name or pin never change it. Existing gyms keep their production ids (`seed-N`, `community-<uuid>`). Never hand-assign ids.

## Human review: `decisions.json`
Keyed by the record's id (shown in the report). Nothing is merged or dropped without one:
```
{"decisions": {
  "g-1a2b3c4d5e": {"decision":"distinct", "reason":"different gym in same building (checked both sites)", "reviewed_against":["seed-102"], "reviewer":"name"},
  "g-9f8e7d6c5b": {"decision":"same-as",  "same_as":"seed-455", "reason":"renamed in 2026"},
  "g-0011223344": {"decision":"reject",   "reason":"duplicate of the other record in this batch"}
}}
```
`distinct` must list **every** candidate in `reviewed_against` (a newly appearing candidate makes the decision stale and puts it
back in review) and needs a reason. `same-as` must name a production candidate. A decision that matches no record blocks the plan.

## Keeping the index current
The index mirrors production (approved spots). Rebuild it read-only from production after every import or if anyone changes
production by other means: `node scripts/gym-import.js build-index --live` (GET only), and check drift any time with
`verify-index --live` (reports gyms added/removed/changed since the index was built). `--from-snapshot <file>` builds from a
saved JSON array instead. Plan against a stale index and you risk re-adding gyms that were added elsewhere.

## Context efficiency (for Claude sessions)
Never read `data/`, `records.ndjson` of old batches, or the index. A session needs only: the new batch's `records.ndjson`
lines it is appending, and `report.md` (≤ ~25 lines per section). All matching runs in the script against the local index
(0.3 s for 2,130 records vs 1,881 gyms). The index holds 9 fields per gym, no notes/photos.

## Production import (not built)
Design constraints for the future `import` command — **not implemented; needs explicit approval of the open questions in
docs/TASKS.md first**:
1. Separate command, requires `--i-understand-this-writes-to-production` **and** `--confirm <first 12 chars of plan_sha256>`; never run by tests.
2. Preflight: `verify-index --live` must be clean; re-plan must reproduce the same `plan_sha256`; batch must be `importable`.
3. Inserts only `ON CONFLICT (id) DO NOTHING`, `status='approved'`, `community=false`, in one transaction, then verify count = before + N.
4. Updates only with a compare-and-swap on the current row (`expect_h` / `updated_at`); a moderator's change since the index was built aborts the batch.
5. Writes `manifest.json` (ids, counts, plan hash, who/when) and rebuilds the index; commit the batch directory.

## Open decisions (need approval before the import command is written)
1. **Mechanism and credentials.** Options: (a) a node script using the `service_role` key from an untracked env var; (b) a generated
   reviewed `import.sql` run via the Supabase CLI; (c) a data migration file. Recommendation: (a) or (b) with the gates above; not (c).
2. **The 3 in-batch duplicate pairs among the 249** (Mad Gym Gwangmyeong, Chamonix Climbing, Climb Days: an English-named and a
   Korean-named record each): which record to keep, or reject both and keep production data. Until decided, 243 are `new`, 6 are held.
3. **How the 249/243 get staged.** They currently exist only in the untracked `data/gyms.reconciled.json`. Options: a one-off
   `stage-from-file` command that writes a committed batch of just the new records, or leave the fixture uncommitted and re-research.
4. **`data/gyms.json` as the offline fallback** (`js/modules/data-load.js`): it is stale against production. Options: replace it later by an
   export from production, or retire the fallback. Nothing changes until you decide.
5. **`supabase/seed.html`**: currently only carries a warning banner. Retire (delete) it, or keep it disabled?
6. **Closures / removals** (a gym that closed) are not modelled: `spots.status` only allows pending/approved. Needs a schema decision.
7. **Updating production content from research** (the 4 gyms whose repo content differs: seed-458 rename, 3 notes appended)
   is possible only through explicit `update` records; say whether to stage those.
8. **New countries** need app support (constants/regions/chips) before their gyms display correctly; the pipeline only warns.

## Never do manually any more
- Add or edit gyms in `data/gyms.json`, or hand-number `seed-N` ids.
- Run `supabase/seed.html` / its generated SQL (**legacy**: its ids no longer match production — running it would overwrite real rows).
- Insert or edit `spots` rows in the Supabase dashboard/SQL editor; change gym content without an `update` record.
- Hand-edit `import/index/*` or a batch's `plan.json`/`report.md`; import a batch that is not `importable`.
- Merge two records "by eye" — record a decision instead.
